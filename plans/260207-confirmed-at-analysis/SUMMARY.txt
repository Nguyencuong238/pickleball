KEY DISCOVERY: TWO-COLUMN DUAL-LOCK SYSTEM
================================================================================

Column 1: lock_expires_at (INTEGER - Unix timestamp)
  - Prevents double-booking during transfer payment verification
  - Set to: time() + (15 * 60) seconds when transfer payment selected
  - Checked: Real-time during slot availability detection
  - Cleared: On booking confirmation or cancellation
  - Status: Fully implemented in FrontController, incomplete in API

Column 2: confirmed_at (TIMESTAMP)
  - Records when admin/owner confirms the booking
  - Set via: Booking::confirm() method
  - Value: now() timestamp when explicitly confirmed
  - Use: Audit trail, compliance tracking
  - Status: Model method complete, not consistently used in all controllers

RELATIONSHIP
  When booking is confirmed, lock_expires_at is cleared and confirmed_at 
  is set. This marks the booking as finalized.

BOOKING LIFECYCLE FLOWS
================================================================================

Transfer Payment (Front/HomeController - CORRECT):
  1. Create → lock_expires_at = now + 15min, confirmed_at = null
  2. Slot LOCKED (cannot double-book)
  3a. Admin confirms → confirmed_at = now, lock_expires_at = null
  3b. Lock expires → Job cancels booking

Transfer Payment (API endpoints - BROKEN):
  1. Create → lock_expires_at = null/job-based, confirmed_at = not set
  2. Slot UNLOCKED (CAN double-book) ← PROBLEM
  3. No confirmation flow → Incomplete state tracking

Cash Payment:
  1. Create → lock_expires_at = null, confirmed_at = null
  2. Slot UNLOCKED (can double-book, expected for cash)
  3. Admin confirms → confirmed_at = now, lock_expires_at = null
